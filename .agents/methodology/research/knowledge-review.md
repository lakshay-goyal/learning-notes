# Knowledge review

Use only when reviewing an existing topic or creating a requested self-test.

1. Read the complete topic package and extract its learning objectives, mechanisms, production decisions, and inspected implementation paths.
2. Build a progressive question map: mental model, mechanism, trade-off, failure/debugging, architecture under constraints, implementation, and source reading.
3. In an interactive review, ask one coherent group at a time and wait for the learner's explanation. Probe reasoning rather than keyword recognition.
4. Evaluate against the existing package and freshly verify any current/version-sensitive claim. Separate a factual error from an incomplete explanation or a legitimate design alternative.
5. Explain gaps with a focused example, then ask a transfer question that tests whether the model now generalizes.
6. Update `revision.md` with demonstrated strengths, weak areas, sections to revisit, exercises, and next review targets only after receiving answers.

Prefer “design under these constraints,” “what fails and why,” “how would you debug it,” and “where is this implemented” questions over random multiple choice. Do not claim to measure retention from an unanswered worksheet.
