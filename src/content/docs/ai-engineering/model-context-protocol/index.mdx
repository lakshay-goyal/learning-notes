## The problem MCP solves

An AI application often needs data and actions from many systems. If each host invents its own discovery format, input schema, invocation method, error model, and lifecycle, integration cost grows roughly with every host–service pair. MCP creates a stable seam between them.

<MentalModel
  title="Protocol, not agent framework"
  icon="⇄"
  model="Think of MCP as the typed conversation between an AI application and a capability provider. The host can discover what exists, call it, and interpret the result without knowing the provider's internal implementation."
  boundary="USB does not decide whether plugging in a device is safe. Likewise, MCP does not choose a model, plan tasks, authorize a user, secure business logic, or make destructive operations reversible."
/>

<Aside type="caution" title="Critical boundary">
Valid protocol framing and schema validation prove that a message has the expected shape. They do **not** prove that the caller may perform the action, that returned content is trustworthy, or that retrying a write is safe.
</Aside>

The important separation is deliberate: the **host** decides what the model may see and call; the **client** speaks the protocol; the **server** publishes a capability surface; the **domain layer** remains responsible for business truth.

## Core primitives

<CardGrid>
  <Card title="Tool · do something" icon="setting">
    An executable operation with described inputs and results: search, create an issue, run a query. A schema helps discovery and validation; it is not authorization.
  </Card>
  <Card title="Resource · read something" icon="document">
    Addressable context or data such as file content, a schema, or a record. The host decides whether and how it enters model context.
  </Card>
  <Card title="Prompt · start something" icon="comment">
    A reusable templated message or workflow starter. It guides interaction but does not enforce security or policy.
  </Card>
</CardGrid>

Clients may also support **elicitation**, allowing a server-side operation to request more user input. Separately negotiated extensions can add behavior such as durable tasks. Core MCP support never implies that every extension is present.

The inspected TypeScript SDK keeps three layers distinct: high-level primitive registration, transport/lifecycle entrypoints, and per-era wire codecs. That prevents every tool handler from branching on protocol revision.

## How it works

### Transport changes delivery, not meaning

<Tabs syncKey="mcp-transport">
  <TabItem label="stdio">
    The client launches and owns a local server process. JSON-RPC frames travel as newline-delimited messages over standard input/output. It fits editor tools, local developer utilities, and per-user process isolation.

    **Operational trap:** stdout is the protocol channel. Send diagnostics to stderr, or a log line can corrupt framing.
  </TabItem>
  <TabItem label="Streamable HTTP">
    Each message is an HTTP POST to one endpoint; the response is JSON or a request-scoped server-sent-event stream. It fits independent deployment, remote access, centralized operations, and many clients.

    **Operational trap:** a stateless handler is not a security perimeter. Authentication, origin/host validation, business authorization, limits, and audit controls still surround it.
  </TabItem>
</Tabs>

Choose stdio when the host can own a local process and that process boundary is useful. Choose HTTP when remote operation, independent scaling, or shared access matter. Neither transport is inherently trustworthy.

### The protocol-era boundary

Do not silently combine tutorials from these eras:

| Concern | `2025-11-25` and earlier | `2026-07-28` |
| --- | --- | --- |
| Opening | `initialize`, then `notifications/initialized` | No required handshake; optional `server/discover` |
| Version/capabilities | Negotiated and retained for a session | Carried in per-request `_meta` |
| Session | May use `Mcp-Session-Id` | Protocol session removed |
| Server needs more input | Server-initiated JSON-RPC request | Returns `input_required`; client retries |
| Horizontal HTTP serving | May require session routing/state | Any instance can handle a self-contained request |

The 2026 revision removed hidden **protocol session state**, not all application state. A workflow can return a durable state handle that the caller includes in the next request.

<Aside type="note" title="SDK version is not the negotiated protocol era">
TypeScript SDK v2 supports the modern revision, but a manually constructed client/server can retain legacy behavior. Use the documented serving and negotiation paths; the example below opts into automatic version negotiation.
</Aside>

## Practical example

<CodeWalkthrough
  title="A minimal typed add tool"
  purpose="This isolates the protocol mechanism: register one tool with input/output schemas, then serve it over stdio."
  annotations={[
    { lines: '1–3', title: 'Use the v2 public entrypoints', explanation: 'McpServer owns high-level primitive registration; serveStdio owns connection lifecycle and era selection.' },
    { lines: '5–8', title: 'Create one server per serving callback', explanation: 'The factory makes lifecycle ownership explicit and keeps tool registration together.' },
    { lines: '10–17', title: 'Declare the contract', explanation: 'Description and schemas drive discovery and validation. Read-only/idempotent annotations are client hints, not enforcement.' },
    { lines: '18–21', title: 'Return for two consumers', explanation: 'Text is model-readable; structuredContent gives host code a typed JSON value and can be output-validated.' },
  ]}
  expected="A client discovers add, calls it with a=20 and b=22, and receives structuredContent { sum: 42 }. The acceptance research executed this path successfully."
>

```ts title="server.ts" {1-3,10-17,18-21}
import { McpServer } from '@modelcontextprotocol/server';
import { serveStdio } from '@modelcontextprotocol/server/stdio';
import * as z from 'zod/v4';

serveStdio(() => {
  const server = new McpServer({ name: 'math-learning-server', version: '1.0.0' });

  server.registerTool(
    'add',
    {
      description: 'Add two numbers',
      inputSchema: z.object({ a: z.number(), b: z.number() }),
      outputSchema: z.object({ sum: z.number() }),
      annotations: { readOnlyHint: true, idempotentHint: true },
    },
    async ({ a, b }) => ({
      content: [{ type: 'text', text: String(a + b) }],
      structuredContent: { sum: a + b },
    }),
  );

  return server;
});
```

</CodeWalkthrough>

<CodeWalkthrough
  title="The client makes modern negotiation explicit"
  purpose="The client launches the stdio server, discovers the tool before calling it, and asserts the typed result."
  annotations={[
    { lines: '4–7', title: 'Opt into version probing', explanation: 'Auto mode probes for the modern protocol and can fall back to a legacy peer.' },
    { lines: '9–14', title: 'The client owns the process', explanation: 'StdioClientTransport launches the executable and connects its protocol streams.' },
    { lines: '16–19', title: 'Discover before use', explanation: 'listTools populates the catalog; the SDK can use cached definitions for validation and mirrored metadata.' },
    { lines: '21–26', title: 'Separate success from transport failure', explanation: 'A successful call returns a result; protocol, SDK, and transport failures can throw through a different surface.' },
  ]}
  expected="The final assertion sees { sum: 42 }, then the client closes the subprocess connection."
>

```ts title="client.ts" {4-7,9-14,16-19,21-26}
import assert from 'node:assert/strict';
import { Client } from '@modelcontextprotocol/client';
import { StdioClientTransport } from '@modelcontextprotocol/client/stdio';

const client = new Client(
  { name: 'math-learning-client', version: '1.0.0' },
  { versionNegotiation: { mode: 'auto' } },
);

await client.connect(new StdioClientTransport({
  command: 'node',
  args: ['dist/server.js'],
}));

const listed = await client.listTools();
assert.deepEqual(listed.tools.map((tool) => tool.name), ['add']);

const result = await client.callTool({
  name: 'add',
  arguments: { a: 20, b: 22 },
});
assert.deepEqual(result.structuredContent, { sum: 42 });

await client.close();
```

</CodeWalkthrough>

## Failure model

The most important production skill is identifying **which boundary failed**:

| Surface | Example | Caller interpretation |
| --- | --- | --- |
| Transport | Process exits, HTTP deadline, stream closes, invalid framing | The exchange did not complete; side-effect outcome may still be unknown |
| Protocol / SDK | Unsupported version/method, malformed JSON-RPC, capability mismatch | Peer or request is incompatible/invalid |
| Tool result | Handler returns `isError: true` | The tool ran and reported a domain-level failure |
| Ambiguous side effect | Caller times out after a write committed | Never blindly retry; reconcile with idempotency/status |

<MentalModel
  title="A timeout is missing information"
  icon="?"
  model="After a write crosses the business boundary, a timeout cannot tell you whether nothing happened, the operation committed, or the response was merely lost."
  boundary="Idempotency keys prevent duplicate intent from becoming duplicate work only when the server stores and reconciles them atomically with operation creation."
/>

For consequential writes, use a stable idempotency key, separate preview from commit, confirm immediately before commit, return an operation ID, and provide status lookup for uncertain outcomes.

The modern stateless core removes protocol-session affinity; it does not remove shared application dependencies. Authorization data, rate limits, databases, queues, caches, and explicit workflow handles still need their own consistency and failure models.

<CardGrid>
  <Card title="Identity and authorization" icon="padlock">
    Authenticate the principal and authorize each operation and record. The model must not choose tenant identity through tool arguments. HTTP tokens must be intended for this resource server and must not be forwarded downstream.
  </Card>
  <Card title="Input and output containment" icon="approve-check-circle">
    Revalidate at domain boundaries, bound result size, sanitize environment inheritance for local servers, and treat resource/tool text as untrusted content that may contain prompt injection.
  </Card>
  <Card title="Reliability and limits" icon="analytics">
    Apply deadlines, concurrency and rate limits, request-size limits, idempotency for writes, stable operation IDs, and explicit cancellation semantics.
  </Card>
  <Card title="Observability" icon="magnifier">
    Record principal, server, tool, authorization decision, outcome, latency, and correlation ID—while redacting tokens, secrets, and sensitive arguments.
  </Card>

<DeepDive summary="Production checklist and test strategy">

- **Authentication:** verify token issuer, audience/resource, expiry, scopes, and signature.
- **Authorization:** test cross-tenant and record-level denials separately from authentication.
- **Consent:** require a meaningful confirmation for destructive or costly actions.
- **Reliability:** test timeout-before-commit, timeout-after-commit, duplicate delivery, worker crash, cancellation, and status reconciliation.
- **Capacity:** load-test realistic tool mixes; `tools/list` and a long external-API call have different cost profiles.
- **Observability:** distinguish protocol rejection, authorization denial, handler/domain failure, and dependency timeout.
- **Privacy:** prove that logs and traces do not expose credentials or full sensitive results.
- **Compatibility:** run current conformance tests and add tests that prevent modern methods leaking onto legacy-pinned connections.

</DeepDive>

## Internals and source-reading path

The source-inspected repository is the official TypeScript SDK at commit [`6032170`](https://github.com/modelcontextprotocol/typescript-sdk/tree/60321700871029401a2e3bed8fdf4f02c9ec3331). Read it in this order:

<Steps>

1. Start with [`examples/tools/server.ts`](https://github.com/modelcontextprotocol/typescript-sdk/blob/60321700871029401a2e3bed8fdf4f02c9ec3331/examples/tools/server.ts) and [`examples/tools/client.ts`](https://github.com/modelcontextprotocol/typescript-sdk/blob/60321700871029401a2e3bed8fdf4f02c9ec3331/examples/tools/client.ts) to see public behavior.
2. Follow registration and `tools/call` into [`packages/server/src/server/mcp.ts`](https://github.com/modelcontextprotocol/typescript-sdk/blob/60321700871029401a2e3bed8fdf4f02c9ec3331/packages/server/src/server/mcp.ts).
3. Follow client behavior in [`packages/client/src/client/client.ts`](https://github.com/modelcontextprotocol/typescript-sdk/blob/60321700871029401a2e3bed8fdf4f02c9ec3331/packages/client/src/client/client.ts) and version probing in `versionNegotiation.ts`.
4. Compare `serveStdio.ts` with `createMcpHandler.ts` to see how connection/request lifetimes select an era.
5. Read `wire/codec.ts` and the modern/legacy registries to see wire differences isolated from primitive handlers.
6. Finish with transport tests and `.github/workflows/conformance.yml`; then deliberately violate an output schema and trace the failure.

</Steps>

<DeepDive summary="Exact tools/call source path">

1. `Client.callTool()` receives the tool name and arguments. A warm discovery cache can enable output validation and mirrored parameter headers.
2. The active transport delivers JSON-RPC. HTTP classifies the request era under a body-size bound; stdio is pinned to an era for the connection.
3. The server entrypoint creates or selects the low-level server and performs lifecycle/capability checks.
4. `McpServer` finds the registered tool, validates arguments using the declared Standard Schema, and invokes the executor with typed input and server context.
5. Declared structured output is validated unless the result is already a tool error or an `input_required` continuation.
6. The active wire codec projects and encodes the result for its era.
7. The client resolves a successful/tool-error result, while protocol, SDK, and transport failures follow throwing/rejection paths.

The [repository analysis](/research/model-context-protocol/repositories/) preserves verified paths, observed failure conditions, and modification exercises.

</DeepDive>

## Alternatives and decision guide

| Approach | Prefer it when | What MCP adds | What MCP costs |
| --- | --- | --- | --- |
| Direct provider tool definitions | One application and model provider own every integration | Portability and independent servers | Another protocol/lifecycle boundary |
| REST/OpenAPI client | Deterministic code calls a known service | AI-oriented discovery and shared primitives | REST may be simpler for fixed calls |
| Bespoke plugin contract | You control every client and need specialized semantics | Shared SDKs and portable capability providers | Bespoke behavior may not map cleanly |
| Queue/workflow engine | Durable async execution and retry are the central problem | A standard way to expose the workflow to AI hosts | MCP core does not supply durable execution |

Do **not** add MCP merely to call an internal function in the same process. Use it when the integration boundary, multiple hosts, independent deployment, or standardized discovery earns its operational cost.
