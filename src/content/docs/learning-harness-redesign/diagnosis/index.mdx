## The two root causes

### Research organised by artifact type

The scaffolder created the same flat siblings for every topic: lesson, plan,
sources, implementation, exercises, revision, optional repositories.

That is convenient for a validator — files either exist or they do not. It is not
a learner journey. Understanding one mechanism meant moving across six document
types, each with its own reading order.

### Visual cardinality hardcoded

The visual validator required exactly one learning page per research slug. The
methodology described four access levels and a page hierarchy; the machine rule
permitted none of it.

The design had route-level progressive disclosure. The implementation had
section-level disclosure inside one route. The gap between those two is the entire
problem.

## The evidence

| Observed | Enforcement point | Consequence |
| --- | --- | --- |
| Same files for every mode | research scaffolder | `quick` and `deep` differ only in length |
| One visual page | visual validator | child pages failed validation |
| Topic ID equals page ID | Astro content schema | pages could not share a topic identity |
| One hardcoded research backlink | research route page | later topics got no visual link |
| Heading-to-anchor coverage | coverage map and validator | reachability was mistaken for teaching |
| Dashboard entry equals topic | dashboard component | splitting would create duplicate cards |
| Manual status strings | README frontmatter | semantic review was not machine-derived |

<Aside type="note" title="How to read this table">
  Each row names a place where a decision became enforcement. That is the useful
  part: an unenforced convention is advice, and an enforced consequence is
  architecture.
</Aside>

## The n = 1 pattern

```text
one high-quality example
  → one successful page
    → one validator written to reproduce that success
      → every future topic forced into the same shape
```

The content was never the problem. The MCP page was thoughtful and source-aware.
Its accidental shape became the platform.

## What was worth keeping

The redesign did not discard the harness. It kept:

- source-backed research
- explicit version boundaries
- a research archive separate from presentation
- preservation of existing work
- deterministic checks before semantic claims
- honest uncertainty labels
- local-first progress privacy

The failure was never evidence discipline. It was the representation and the
cardinality.

## Five questions before changing a prompt

```bash
git status --short --branch
```

1. Which file or schema forces this shape?
2. Which validator rejects the alternative?
3. Which component assumes the shape at runtime?
4. Which documentation claims an enforcement the code does not provide?
5. Can a small fixture prove the desired alternative before migrating content?

<details>
<summary>Why this order matters</summary>

If the model receives a better decomposition prompt while the validator still
rejects multiple pages, the model will either ignore the prompt or compress its
work. Fix the machine contract first; then improve the prompt.

</details>

<Aside type="tip" title="Try it">
  Question 4 is the one people skip, and it is the one that finds dead config.
  `.agents/config.json` once carried 22 keys that no code read: documentation
  promising enforcement that did not exist.
</Aside>
